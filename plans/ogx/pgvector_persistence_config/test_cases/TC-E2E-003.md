# TC-E2E-003: Base-config-only CR generates no config and reports ConfigGenerationInactive

**Objective**: An `OGXServer` that sets none of `spec.providers`, `spec.resources`, `spec.storage`
or `spec.disabledAPIs` generates no ConfigMap and reports `ConfigGenerationInactive`, so the fix
cannot alter a base-config-only deployment.

**Preconditions**:

- Environment per Section 3.1 of the plan
- ConfigMap `ogx-base-config` (key `config.yaml`) exists in `ogx-pgvector-test` with the label
  `ogx.io/watch: "true"`. Its content does not matter here, because the CR declares nothing that
  triggers generation

**Test Steps**:

1. Apply the `OGXServer` CR from Test Data
2. Wait 120s for condition `ConfigGenerated=false` on `ogxserver/ogxserver-base-only`
3. Read the `reason` and `message` of the `ConfigGenerated` condition
4. Read `status.configGeneration`
5. Count ConfigMaps labelled `ogx.io/generated-config` whose name begins
   `ogxserver-base-only-config-`
6. List `spec.template.spec.volumes[*].configMap.name` on `deployment/ogxserver-base-only`

**Expected Results**:

- Step 3 prints reason `ConfigGenerationInactive` and the message
  `Declarative config generation is not active`, because `HasDeclarativeConfig()`
  (`api/v1beta1/ogxserver_types.go`) returns false for this CR
- Step 4 prints nothing, since `clearConfigGenerationStatus` nils `Status.ConfigGeneration`
- Step 5 prints `0`
- Step 6 prints no `ogxserver-base-only-config-<hash>` name and no `ogx-base-config` entry.
  `spec.baseConfig` is an input to generation, not a runtime config the pod mounts. An unrelated
  ConfigMap volume such as the managed CA bundle does not count

**Test Data**:

The TC-E2E-001 CR with `metadata.name: ogxserver-base-only` and the whole `spec.providers` block
removed, so the CR carries only `distribution`, `baseConfig` and `workload`.
