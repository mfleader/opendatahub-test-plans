# TC-E2E-002: OGX server pod reaches Running with declarative pgvector against live PostgreSQL

**Objective**: An `OGXServer` with a declarative pgvector provider starts and stays `Running`
against a reachable PostgreSQL with the `vector` extension, with no `AttributeError` in the pod
logs.

**Falsifiability**: reverting `expandPgvectorProvider` to `be51587` makes step 10 print nothing
and the pod crash, so steps 4 through 8 fail as well.
**Preconditions**:

- All preconditions of TC-E2E-001
- `ogx-base-config` carries no `vector_stores` block
- The PostgreSQL fixture from Section 3.5 of the test plan is applied in `ogx-pgvector-test` and
  reachable as host `postgres` on port `5432`, database `postgres`, user `postgres`, whose
  password matches Secret `postgres-secret`
- `psql` is available on the test harness, or `oc exec` into the PostgreSQL pod is permitted

**Test Steps**:

The server pod carries the label `app.kubernetes.io/instance=ogxserver-rh`.

1. Confirm the extension with
   `psql -U postgres -d postgres -tAc "SELECT extname FROM pg_extension WHERE extname = 'vector';"`
2. Apply the TC-E2E-001 CR if absent
3. Wait 120s for `ConfigGenerated=true`, then read `vector_stores.default_provider_id` from the
   generated `config.yaml`
4. Wait 300s for the pod to reach `Ready`
5. Record that pod's phase and `containerStatuses[?(@.name=="ogx")].restartCount`
6. Read `status.phase` on the OGXServer
7. Count the crash signature across all containers in the pod logs, and separately count lines
   beginning `ERROR`
8. List events with `reason=BackOff`
9. Wait 300s for `Ready=false` on the same pod, then repeat step 5
10. Read the pgvector entry's `config.persistence` from the generated ConfigMap
11. In the server pod, run `curl -sf localhost:8321/v1/providers`

**Expected Results**:

- Step 1 prints `vector`
- Step 3 prints `null`. Any other value means the base config violates the precondition, so the
  case fails without proceeding (Section 8, risk 1)
- Step 5 shows phase `Running` with restart count `0`
- Step 6 prints `Ready`
- Step 7 prints `0` for both counts
- Step 8 lists no `BackOff` event for the server pod
- Step 9's wait times out, so the pod never left `Ready`, and the repeated step 5 still shows
  `Running` with restart count `0`
- Step 10 prints `backend: kv_default` and `namespace: vector_io::pgvector`. Without this the case
  rests on a log-string count alone, which a server that stopped raising would satisfy
- Step 11 lists an entry with `api: vector_io`, `provider_id: pgvector`, and a `config.persistence`
  of `{backend: kv_default, namespace: vector_io::pgvector}` echoed back by the server. That echo is
  the server confirming it parsed and accepted the block the operator emitted. Its `health.status`
  is `Not Implemented`, because the pgvector provider implements no health check, so health is not
  a usable signal here
